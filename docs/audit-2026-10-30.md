# Vibecraft correctness and performance audit

Update: the eight findings below are historical observations of version 0.1.0. Corrections and regression evidence for 0.1.1 are recorded in release-0.1.1.md.

Reviewed current commit 7b58f3a on 30 October 2026. This is a whole-project audit, not a comparison against VideoScribe or a review limited to the last commit. Application sources and the delivered ZIP were left unchanged. The only new project document is this report; generated fixtures and evidence are in ignored .runtime/ and artifacts/audit-20261030/.

Build and all 36 existing unit/integration tests passed. Additional isolated browser, renderer, FFmpeg and launcher probes confirmed eight issues that the existing tests do not cover. Existing browser saves were not used. Test-owned browsers and servers were closed.

## Standards: implementation and performance findings

These are concrete implementation problems, not style violations or speculative code smells. The project has no separate performance standard; the practical target is responsive editing and preview consistent with its 24/30 fps export settings.

### S1 — P2: every thumbnail prepares the entire project's media

Locations: [Timeline.tsx:14](../src/Timeline.tsx#L14), [render.ts:28](../src/engine/render.ts#L28), [SceneNavigator.tsx:13](../src/SceneNavigator.tsx#L13).

Each SceneThumb independently runs prepareImages(project), which decodes images from all scenes. The stage does the same. The thumbnail render effect also depends on the entire project, so unrelated edits redraw every scene.

Reproduction: import a valid project with 25 scenes sharing a single small PNG. Instrument HTMLImageElement.decode and canvas clearRect in an isolated browser context. Opening it triggered 26 image decode calls. Changing only the project title triggered 26 canvas clears. These are measured call counts, not a claim that Chrome necessarily stores 26 independent copies of decoded pixels. With distinct large images and complex scenes the repeated work becomes substantially more expensive.

Fix: share prepared image/font resources by source identity; load only required media; memoize thumbnails by the relevant scene, camera and resources rather than the entire project. Avoid decoding again when an unrelated element changes the source-key string.

### S2 — P2: unrelated edits recreate all audio players

Locations: [App.tsx:43](../src/App.tsx#L43), [App.tsx:58](../src/App.tsx#L58).

edit() clones the entire project, changing the project.audio array identity even for a title or geometry edit. The audio effect depends on that array and destroys/reconstructs every HTMLAudioElement with preload=auto. Reproduction: a valid fixture with 50 small clips constructed 50 new Audio objects for a single project-title edit. Potential playback interruptions were not measured; the unnecessary construction/preload churn itself was confirmed.

Fix: retain audio nodes by track ID/source and update playback parameters without rebuilding nodes. Separate content changes from transient editor/transport state, or use structural sharing so unrelated edits preserve audio identity.

### S3 — P2: complex vector geometry is prepared again every frame

Location: [render.ts:68](../src/engine/render.ts#L68).

renderVector reparses, scales, serializes and splits every visible path for each frame. pathCache only helps after the transformation and serialization have already occurred. Completed drawings also incur this work.

Measured 1920×1080 static-frame CPU costs, with valid generated projects containing 40 paths per element and 100 line segments per path:

| Vector elements | Median render time | Maximum of 7 measured frames |
| --- | ---: | ---: |
| 1 | 5.7 ms | 6.1 ms |
| 10 | 33.4 ms | 39.9 ms |
| 25 | 73.0 ms | 79.1 ms |

For comparison, 24 fps allows about 41.7 ms per frame and 30 fps about 33.3 ms. These are headless CPU timings on this PC; GPU raster/compositing and React work are excluded, so they are not measured interactive FPS or a hardware-independent guarantee. A simpler 150-element original-art fixture was much cheaper: median 5.1 ms across 40 samples. Complexity of imported paths matters more than element count alone.

Fix: cache expanded/transformed paths, per-subpath metrics and total lengths by immutable path content and dimensions. Consider cached layers for completed static drawings and a total path/segment complexity budget on import.

## Spec: behavior and output correctness findings

Expected behavior comes from README.md, docs/implementation-status.md, docs/portable-package.md and the existing preview/export contracts. Documented missing commercial services/features are outside this defect list.

### B1 — P1: the editor can autosave a project it cannot reopen or export

Locations: [App.tsx:98](../src/App.tsx#L98), [App.tsx:130](../src/App.tsx#L130), [Stage.tsx:54](../src/Stage.tsx#L54), [storage.ts:20](../src/storage.ts#L20), [validation.ts:68](../src/validation.ts#L68).

The parser limits scenes to 150 elements, total projects to 500 elements, and duration to 600 seconds. Several mutations bypass equivalent admission checks. Duplicate, paste and direct canvas creation are examples; scene duplication and freely edited labels/timings can violate other schema limits. Raw autosave does not validate them.

Confirmed UI sequence: import a valid 150-element fixture, select all, duplicate, wait for autosave. The saved scene contained 300 elements. parseProject rejected it, and video admission returned HTTP 400. Reloading the browser opened the starter project "From spark to story" and showed a parse-error toast instead of reopening the saved fixture. The invalid record remains in IndexedDB; this is not proof its data was physically deleted, but normal reopening/exporting fails and work recovery is obstructed.

Fix first: enforce admission centrally before committing mutations, with efficient incremental checks for common edits. Do not validate/decode every embedded asset on every pointer movement. Keep invalid/recoverable saves available for download or repair instead of falling back without a recovery path. Add boundary tests for duplication, paste, scene duplication, text/name limits and cumulative duration.

### B2 — P2: fade transitions can flash even between identical scenes

Location: [render.ts:293](../src/engine/render.ts#L293).

The incoming scene's fade alpha applies to its background and then each drawing individually. This differs from crossfading complete rendered frames. A live pixel probe used two identical white scenes containing an identical opaque black rectangle: its center was RGB (0,0,0) before the transition, but RGB (64,64,64) at the fade midpoint. An unchanged black object should remain black throughout a crossfade.

Fix: render the incoming complete scene into an offscreen canvas and composite it once with the transition alpha, or blend two complete scene buffers. Add a pixel regression for identical scenes and overlapping opaque objects.

### B3 — P2: audio fade settings produce different preview and exported levels

Locations: [exports.ts:31](../server/exports.ts#L31), [timeline.ts:103](../src/engine/timeline.ts#L103), [AudioPanel.tsx:200](../src/AudioPanel.tsx#L200).

Export clamps fade duration to the trimmed clip's length. Preview uses the stored, unclamped duration. The UI accepts fades longer than a trimmed clip, so both calculations can disagree after normal trimming/editing.

Confirmed with the actual generated FFmpeg filter: a one-second constant-amplitude 0.1 signal with a ten-second fade-in had predicted preview sample amplitude 0.005 at 0.5 seconds. FFmpeg output was 0.0500000007: approximately 10× the preview amplitude. This measures signal amplitude, not subjective perceived loudness. No real user audio was used.

Fix: share one effective-fade calculation across timeline preview, audio-panel playback and export; normalize or constrain fades when trimming. Regression-test fades longer than a clip, including the default fade-out after short trims.

### B4 — P2: concurrent AI storyboard requests bypass the busy gate

Location: [services.ts:68](../server/services.ts#L68).

generateScript checks aiBusy, awaits aiStatus(), and only then reserves the busy flag. Two tabs can pass the check together and submit simultaneous expensive model calls. The first completion also clears busy while the second is still running.

An isolated LocalServices execution with gated fetch stubs confirmed two generation calls, peak concurrency two, and both requests fulfilled. No real Ollama model call was made. This proves the concurrency defect; actual model latency/GPU-memory impact was not benchmarked.

Fix: reserve busy before the first await and release it in an outer finally covering status lookup, validation and generation. Add a concurrent-request test expecting one 409 response.

### B5 — P2: changing the portable port leaves the first server unmanaged

Locations: [portable-launcher.mjs:43](../scripts/portable-launcher.mjs#L43), [portable-launcher.mjs:60](../scripts/portable-launcher.mjs#L60).

The launcher permits an explicit second port while the saved session is running, then overwrites its one ownership file. Real reproduction using only the staged test package: start on 4521, then start the same folder on 4522. Both servers were live, but the ownership file recorded only 4522. Stop closed 4522 and removed the file; 4521 remained live. The test retained the first token privately, restored ownership and stopped that server too.

Fix: check the saved owned session before accepting a port change, rejecting the second launch or offering an orderly switch. Alternatively maintain ownership records per port/session. Add a start/change-port/stop lifecycle regression.

## Additional capacity risk

Repeated packaging/verification preserves every staging directory, archive and extracted test copy. On this PC, .cache/portable-verification occupied 6,247,299,639 bytes and artifacts/releases occupied 3,026,628,142 bytes: about 9.27 GB combined. These are development/test artifacts, not a proven application memory leak. No files were deleted during the audit.

Export jobs/files are also retained without an expiry or bounded history; current .runtime/exports occupied only about 20 MB, so significant export-driven disk pressure was not demonstrated. Provide explicit user-controlled cleanup/retention with completed outputs protected until downloaded or retained intentionally. Avoid cleaning personal browser saves or media as part of cache cleanup.
